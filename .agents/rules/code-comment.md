# 通用代码注释规则

本文件仅用于约束 Agent 在生成、修改、重构和审查代码时的注释行为。规则适用于不同语言和项目；具体注释语法、文档格式和项目既有约定优先于本文件中不冲突的通用建议。

## 核心要求

- 注释阅读对象是代码维护者和 AI，目标是降低理解、维护和排查成本。
- 假定读者是熟练的开发者：熟悉所用语言、常用数据结构和通行惯用法。语言语义、标准库行为、常见算法以及一眼可见的逻辑都不需要解释。
- 注释是例外而非默认。多数函数不需要注释；下笔前先确认读者无法仅凭命名与代码结构获得该信息。
- 注释的读者以中文为主语言，默认用中文书写。代码标识符、协议名、API 名称、标准术语和必要的专有名词保留通用写法。
- 注释应简约、干练、准确，优先表达有维护价值的信息。
- 注释只描述代码的行为和结果，以及维护者必须遵守的约束、边界和风险；不解释原因，不重复代码已经清楚表达的内容。
- 注释不写 Agent 的思考过程：不记录推理、权衡、尝试过的方案、生成或修改经过，也不写无关的开发日志。
- 注释必须与实现保持一致；代码行为发生变化时，应同步检查并更新相关注释。

## 注释内容

### 实现代码

对实现代码，只在以下地方添加有信息量的注释：

- 巧妙、晦涩、有趣或不符合直觉的实现。
- 重要的业务规则、算法不变量、状态转换或关键数据处理。
- 容易误改、误用或引发缺陷的内部逻辑。
- 复杂条件、边界处理、异常分支、并发同步、资源生命周期和性能敏感处。
- 因兼容性、平台差异、第三方缺陷或安全约束而采用的特殊写法。

实现代码的注释说明这段代码的行为与结果、依赖的前提，以及修改时必须保持的约束；不说明为什么这样实现，也不逐行翻译代码的执行过程。例如写“访问共享计数前必须关中断”，而不是“考虑到可能存在并发，这里选择关中断”。

概括可见的控制流同样属于过程注释。把分支、赋值、循环、提前返回改写成一句自然语言描述（例如“失败时不改动状态”“这里只重置计数”“某条件下只处理能容纳的部分”），读者从代码本身即可得到，应当删除。

### 对外接口

对外公开的函数、类、模块、组件、配置项、数据结构和接口，应根据项目文档约定添加文档注释，至少说明调用者需要知道的内容：

- 用途和解决的问题（what）。
- 输入参数、返回值、错误或失败条件。
- 调用前提、默认行为、限制、线程安全性和副作用（如适用）。
- 不明显的边界条件或调用顺序要求（如适用）。

接口注释面向使用者，重点说明“能做什么、如何使用、有什么限制”；不要把内部实现步骤或 Agent 的思考过程写进接口文档。

返回值说明必须给出调用者无法从签名推断的信息。仅重复返回类型名，或使用与函数名同义的“成功／失败”之类措辞，都不构成说明。失败条件应列全：若同一个失败返回值对应多种失败情形，要么逐一列出，要么明确告知调用者无法区分。

## 添加与省略

### 应添加

- 读者无法仅凭清晰命名和代码结构快速理解的关键行为或结果。
- 代码正确性依赖的不明显前提、约束或边界条件。
- 维护者修改时最容易破坏的关系、顺序、生命周期或兼容性要求。
- 业务规则、协议规定或外部限制中代码无法直接体现的内容。
- 已知但暂时无法修复的限制或风险；应说明影响和可追踪的后续事项。此项仅适用于已实现但存在缺陷的代码。

### 应省略

- 对赋值、循环、条件、函数调用和变量名的逐行翻译。
- 对可见控制流的概括性描述，包括分支作用、状态重置、失败后是否改动等能从代码直接读出的内容。
- 重复函数名、参数名、类型名或明显控制流的注释。
- “处理数据”“进行判断”“执行操作”等没有额外信息的空话。
- 代码尚未编写、空实现或占位文件的状态说明。缺失的功能不需要注释解释，保持文件与函数的默认形态即可。
- 同一条信息在接口文档与实现注释两侧重复。选择读者会先看到的一侧，另一侧不再复述，避免两份副本各自漂移。
- 实现原因与设计取舍的论证、度量数据、备选方案比较和决策过程。代码中只保留必须遵守的约束，其余交由设计文档承载。
- Agent 的决策叙述，例如“我改为……因为……”“考虑过 A，最终选择 B”“为修复上一步的问题而调整”“按用户要求改成……”。这类内容属于对话或提交记录，不属于代码。
- 无依据的推测、个人情绪、夸张评价和与代码无关的背景。
- 仅用于记录历史变更的内容；历史应交由版本控制系统记录。
- 没有上下文的 `TODO`、`FIXME` 或其他占位词。确需保留时，应说明问题、影响和可执行的后续条件。
- 可以通过改善命名、拆分函数或简化结构解决的可读性问题。

## 表达与格式

- 遵循目标语言标准注释语法、文档注释格式、项目术语和现有风格。
- 注释应短而具体，说明行为、结果或约束，不追求注释数量和篇幅。
- 一行能说清的不拆成多行；限定条件优先并入首行说明，而不是另起一条。
- 注释篇幅应明显短于被说明的代码。当一条注释需要分段展开时，说明信息应当外移到设计文档。
- 注释应尽量靠近被说明的代码；一条注释只承担清晰、相关的一组说明。
- 不使用装饰性分隔线、无意义标签或夸张措辞；保持同一文件和项目内的格式一致。
- 不得以本文件为由批量改写项目既有的注释格式惯例，例如既有的分节方式或文档标签选择；此类冲突按末节优先级处理。
- 版权声明、许可文本、作者署名等非说明性内容不受本规则约束，不要删改。
- 术语在代码注释、接口文档和面向用户的文档之间保持一致，同一概念不要出现多个称法。
- 注释中引用的内容若含有注释分隔符或转义序列，需确认不会提前结束注释或破坏其结构。
- 示例、命令、配置值、版本、链接和性能数据必须有依据；失效时及时更新或删除。
- 不在注释中写入密码、令牌、个人信息、内部地址或其他敏感数据。

## Agent 工作流程

### 编写或修改代码前

1. 阅读目标代码、邻近实现、相关测试、调用方和适用规则。
2. 判断本次变更是否需要新增、修改或删除注释。
3. 区分注释对象是实现代码还是对外接口，并按对应章节确定要写的内容。
4. 对业务规则或协议约束没有依据时，不得猜测成事实；应查找依据或向用户提问。

### 变更完成后

- 检查新增注释是否提供了代码本身没有表达的信息。
- 检查注释是否准确、简洁，并符合目标项目的注释格式。
- 逐条确认没有残留过程注释，包括对可见控制流的概括性描述和 Agent 的决策叙述。
- 检查是否存在同一信息在接口与实现两侧重复，或本应外移到设计文档的论证性内容。
- 检查实现、测试、接口行为和注释是否一致。
- 检查是否残留过期注释、失效示例、错误链接、复制粘贴内容或无上下文的待办事项。
- 检查是否可以通过改善代码结构减少注释，而不是继续堆叠说明。
- 确认注释改动没有影响代码语义；纯注释重构应当不改变任何可执行内容。

## 优先级

发生规则冲突时，按以下顺序处理：

1. 语言、框架和项目已有的强制性规范。
2. 对外接口必须清楚表达用途、输入输出和限制。
3. 实现代码必须写明关键逻辑的约束和维护风险。
4. 简洁、准确，避免重复和无效信息。
5. 同等条件下少写优于多写：无法判断一条注释是否有维护价值时，删除它。
